CSV is the canonical format for fiscode data. One file holds all the data you entered, laid out as
**one small table per record type**: profile, clients, income, expenses and so on. It is meant to be opened in
Excel, Google Sheets or Numbers and read by a person, and to load back into fiscode without losing
anything.

The layout lives in `packages/csv/src/sections.ts`. The stored fields live in
`packages/csv/src/schema.ts`.

## What the file looks like

```
# fiscode export (schema: v4; scope: full)
# Money is in dollars. Dates are YYYY-MM-DD. Import this file at https://fiscode.app to restore it.

# Income
record_type,date,client_name,amount,source_type,source_type_label,income_kind,income_kind_label,description,notes,id,client_id,created_at,updated_at,deleted_at
income,2026-01-15,Stable Commission Co,10000.00,1099,1099 self-employment,recurring,Recurring,January retainer,,in_01…,cl_01…,2026-06-04T12:00:00.000Z,2026-06-04T12:00:00.000Z,

# Expenses
record_type,date,category,category_label,description,amount,client_name,reason,flag_for_section_179,startup_expense,placed_in_service_date,notes,id,client_id,created_at,updated_at,deleted_at
expense,2026-01-20,equipment,Equipment,Standing desk,899.99,,Home-office setup stipend purchase.,yes,no,,,ex_01…,,2026-06-04T12:00:00.000Z,2026-06-04T12:00:00.000Z,
```

Each table has three parts:

1. A title line that starts with `#`, such as `# Income`. It is a comment; the importer skips it.
2. A header row. Its first cell is always `record_type`.
3. One row per record. The first cell names the record type.

Within a table the readable columns come first (date, name, amount, category) and the ids and
timestamps come last. Rows are in date order, then id order. A record type with no rows is left
out of the file.

The **full export holds every row, including deleted ones**. Deleting in fiscode is a soft delete:
the row stays and gets a `deleted_at` time. Deleted rows are written in a table of their own,
right after the live table of the same record type, with a title that says so:

```
# Expenses
record_type,date,category,…
expense,2026-01-20,equipment,…

# Expenses (deleted - not part of your books)
record_type,date,category,…
expense,2026-02-02,supplies,…,2026-08-01T09:30:00.000Z
```

They come back deleted on import, so a restore never turns a delete into a permanent one. Do not
add them to your totals.

The **yearly export leaves deleted rows out**. It is the file for your accountant, so the amounts
in it add up to what the app shows.

The file holds **nothing that depends on when or where it was exported**. Two exports of the same
data are the same bytes. The export date is in the file name instead.

### What is in the file, and what is not

| In fiscode                                    | Full export              | Yearly export           |
| --------------------------------------------- | ------------------------ | ----------------------- |
| Profile, clients, vehicles                    | yes                      | yes                     |
| Income, expenses, mileage, time, retirement   | yes                      | rows dated in that year |
| Entity, spouse and home-office spans          | yes                      | spans that overlap it   |
| Deleted rows                                  | yes, in their own tables | no                      |
| Edit history (the log behind `/history`)      | yes                      | no                      |
| Downloaded tax figures (the `/tax-data` page) | no                       | no                      |

The downloaded tax figures are a cache. fiscode fetches them again by itself, so they are never
exported.

The **History** table is the last one in a full export. Each row is one change: when, what kind
(`insert`, `update`, `delete`, `revert`), which record, and the record before and after as JSON
text. It is there so a restore brings the log back; it is not meant for reading. An import also
logs itself as one history row that holds the whole state from before the import, so a file from
an app that has imported before can be much larger than its data.

**Keep the original download of a full backup.** Spreadsheets cap a cell at about 32,000
characters and cut off the rest when they save. A full backup that has been opened and saved in a
spreadsheet may hold a cut-off history cell. The importer checks each history cell and rejects the
file, naming the row, rather than restore a broken log. The yearly file has no history and is safe
to edit and save.

## Two workflows

1. **App-first** — enter rows in the web app, click **Export** when you want a CSV (for backup,
   handoff to an accountant, or to load on a different device). This is the common path.
2. **CSV-first** — author the CSV yourself (in Excel, Numbers, a text editor, a script), then
   **Import** it into the app. Everything you can do in the UI you can do directly in CSV.

Both paths produce identical state.

## How values are written

| Kind         | Written as            | Example                    | Notes                                                                 |
| ------------ | --------------------- | -------------------------- | --------------------------------------------------------------------- |
| Money        | Dollars, two decimals | `1234.56`                  | No `$`, no thousands separator, so a spreadsheet reads it as a number |
| Percent      | Percent, two decimals | `6.00`                     | Only `default_commission_rate_percent`                                |
| Date         | ISO `YYYY-MM-DD`      | `2026-01-15`               | Anything else is rejected on import                                   |
| Timestamp    | ISO 8601 with `Z`     | `2026-06-04T12:00:00.000Z` | `created_at`, `updated_at`, `deleted_at`                              |
| Yes / no     | `yes` / `no`          | `yes`                      | Import also accepts `1` / `0`                                         |
| Code         | The stored code       | `software_subs`            | A `…_label` column beside it gives the human name                     |
| Whole number | Digits                | `480`                      | Minutes, miles, square feet, dependents                               |

fiscode stores money as integer cents. The file shows dollars because that is what a person reads;
the importer converts `1234.56` back to `123456` exactly, with no floating-point step.

### Label columns are for reading only

These columns are computed on export and **ignored on import**. Edit the code or the id beside
them, not the label:

- `filing_status_label`, `quarterly_method_label`, `entity_type_label`, `source_type_label`,
  `income_kind_label`, `deduction_method_label`, `category_label`, `account_label`
- `client_name` — the name of the client in `client_id`
- `vehicle_name` — year, make and model of the vehicle in `vehicle_id`
- `hours` — `minutes` divided by 60

### Quoting and spreadsheet safety

- A cell that contains a comma, a double quote or a line break is wrapped in double quotes, with
  inner quotes doubled (RFC 4180). Lines end in CRLF.
- The file starts with a UTF-8 byte-order mark so Excel reads accented and non-Latin characters
  correctly. The importer accepts files with or without it.
- A text cell that starts with `=`, `+`, `-` or `@` (or a tab or carriage return, which some
  spreadsheets skip over) would be run as a formula by a spreadsheet. The export puts a `'` in
  front of it (`'=SUM(A1)`), and the importer takes it off again. A text cell that already starts
  with `'` gets one more for the same reason. Amounts are never guarded,
  so `-50.00` stays a number.

## Authoring tips

- **Column order doesn't matter** on import; the parser keys on each header row. You can also
  leave out any column you don't need.
- **Start every header row with `record_type`**, and every data row with the record type.
- **IDs must be unique within a record type.** They can be any string; ULIDs are what the app
  emits. A simple convention works fine for hand-authored files: `in_001`, `in_002`, …
- **The profile row is a singleton.** Its `id` is always the literal string `profile`.
- **Timestamps can be left empty** in a hand-authored file.
- **Money has at most two decimals.** `1234.5` and `$1,234.56` are accepted; `1234.567` is
  rejected rather than rounded.
- **Keep dates as `YYYY-MM-DD`.** Spreadsheets like to show and save dates in the local format.
  If a date comes back as `3/4/2026`, the importer rejects that row and tells you, because it
  cannot know whether that is March 4 or April 3. Format the date columns as `yyyy-mm-dd` before
  saving.
- Blank lines and `#` lines are skipped anywhere in the file.

## Provenance header

Each export begins with two `#` lines. The first holds the schema version and the scope (`full`,
or `yearly` plus the year). The second says how to read the file. A spreadsheet shows them as
text in column A. You can omit them in a hand-authored file.

```
# fiscode export (schema: v4; scope: yearly; year: 2026)
```

## Old files (schema v1)

Before schema v2, fiscode wrote one wide table: a single header with every column for every
record type, money in integer-cent columns named `…_cents`, and `1` / `0` for booleans.

```
# schema: v1
record_type,id,created_at,updated_at,deleted_at,filing_status,…,amount_cents,…,account
income,in_01…,2026-06-04T12:00:00.000Z,…,1000000,…
```

**Those files still import.** The importer does not switch on the version. It reads every file
with the same three rules — `#` lines are comments, a row starting with `record_type` is a
header, anything else is a row under the header above it — and the **column name** says how to
read a cell: `amount_cents` is integer cents, `amount` is dollars. A v1 file is simply a file
with one header and cents columns. You can even mix the two styles in one file. If one row fills
both `amount` and `amount_cents`, they must agree; a row where they differ is rejected.

A few v2 headers are longer than the v1 name so they read clearly on their own. The importer
accepts both:

| v2 header                         | v1 name                                    |
| --------------------------------- | ------------------------------------------ |
| `entity_type`, `client_type`      | `type`                                     |
| `income_kind`                     | `kind`                                     |
| `model_year`                      | `year`                                     |
| `deduction_method`                | `method`                                   |
| `amount`, `annual_w2_wages`, …    | `amount_cents`, `annual_w2_wages_cents`, … |
| `default_hourly_rate`             | `default_rate_cents`                       |
| `default_commission_rate_percent` | `default_commission_rate_basis_points`     |

v1 files also had an `# exported:` time line. It is read and ignored.

The `schema:` marker is used for one thing: a file marked `v1` never carried the `'` formula
guard, so its text is kept exactly as written.

Exports are always written as v4. Schema v4 adds four profile columns, `prior_year_total_tax`, `prior_year_agi`, `prior_year_state_tax` and `prior_year_figures_year`; schema v3 added `placed_in_service_date` on expenses. v1, v2 and v3 files still import, with the newer columns empty. An app version older than v4 refuses a v4 file rather than read it wrongly.

## File names

- **Download &lt;year&gt; CSV** writes `fiscode-<year>-tax-year.csv`. This is the file for your
  accountant.
- **Download full CSV** writes `fiscode-full-backup-<date>.csv`. This is your portable backup.

## Import modes

You choose the file first. The app reads it, tells you how many rows, deleted rows and history
entries it holds, and then asks what to do with it. Nothing changes until you confirm.

- **Restore** — replace everything in the app with the file. Use this for a full backup. The
  dialog says how many rows are replaced and how many rows in the app are not in the file.
- **Add rows** — keep everything in the app and add the file's rows whose `id` is not there yet.
  Rows already there are skipped and stay as they are; the dialog counts them.

Neither is chosen for you. Three cases differ:

- **An empty app** (a new install): there is nothing to keep, so there is no question. The setup
  screen has **Restore from a backup**, and the file brings its own profile. A full export
  restored this way exports again as the same bytes.
- **A yearly file**: Restore is refused once the app holds data, because a yearly file holds one
  year and no deleted rows. Add rows still works.
- **A file with no rows, or one that is not a fiscode CSV**: refused, with the reason on screen.

An import is all or nothing. If any row cannot be written, or the page is closed before it
finishes, the app is exactly as it was.

Every import over existing data appends a history entry holding the full pre-import state.

## Validation

The importer checks every row rather than stopping at the first bad cell. A file with any
rejected row is not imported at all. The app lists the first ten problems in the import card, with a
count of the rest, and keeps them there until you choose another file. Each has the
row number as your spreadsheet shows it, the record type, the column, and what was expected:

```
Row 50 (expense): amount: Expected a dollar amount with at most two decimals, like 1234.56, got "899.999"
Row 27 (income): date: Expected a date as YYYY-MM-DD, got "1/15/2026". In a spreadsheet, format the column as yyyy-mm-dd before saving
```

Common rejections:

- **Unknown `record_type`** — a typo, or a record type the running app doesn't recognize.
- **A money cell it cannot read exactly** — `ten`, `1e3`, or more than two decimals.
- **A date that is not a real `YYYY-MM-DD` date** — `1/15/2026`, and also `2026-02-30`.
- **Dollar and cents columns that disagree** in one row.
- **A schema marker this version does not know** — the file was written by a newer fiscode.
  Update the app, then import again.
- **A non-integer in a whole-number or `…_cents` column** — e.g. `amount_cents: 12.50`.
- **Missing `se_start_date` on `profile`** — required; the tax engine uses it to gate which rows
  count toward the year.
- **Bad yes / no values** — `yes`, `no`, `1`, `0` or empty only.
- **A row before any header row.**
- **A history cell that is not complete JSON** — a spreadsheet cut it short. Import the original
  download.

## Round-trip guarantee

- Two exports of the same data are the same bytes, whenever and wherever they are made.
- `Full export → restore into an empty database → full export` gives back the same bytes: the
  same rows, deleted ones included, and the same history.
- Old v1, v2 and v3 files import to the same state and re-export as v4.

These are enforced by vitest tests in `packages/csv/src/format.test.ts` (against a saved v1
fixture) and `packages/db/src/repo/sync.test.ts` (through a real database).

Three things to know about that guarantee:

- **It is about an empty database.** An import over existing data adds one history row holding
  the state from before the import, so that import can be reverted. The next export then has
  that extra row. Today the app asks for a short setup before it shows the import card, so a
  restore in the app is an import over that setup; restoring straight into an empty app is
  planned.
- **An empty text field and a missing one are the same cell.** Both are written as an empty cell
  and read back as "no value".
- **The export refuses to write what it could not read back.** If a stored date is not
  `YYYY-MM-DD` (possible in data imported by an older version), the export stops and names the
  row. Fix that row in the app, then export again. An old v1 file that holds such a date is
  rejected on import for the same reason; correct the date in the file first.
